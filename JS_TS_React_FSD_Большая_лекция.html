Основы функций

Функции — фундамент всего JavaScript. Разберём, как они устроены, какие бывают, и сразу запустим код прямо здесь. Жми ▶️ под примерами — увидишь реальный вывод.

01 · ЧТО ТАКОЕ ФУНКЦИЯ

Функция — это станок

Берёт что-то на вход, отдаёт что-то на выход. Один раз настроил — пользуешься сколько угодно.

Смысл простой. Есть кусок работы, который повторяется. Вместо копирования по всему коду — заворачиваешь в функцию и зовёшь по имени. Поменялась логика — правишь в одном месте.

function.js
// объявляем функцию
function greet(name) {
  return 'Привет, ' + name + '!';
}
 
// зовём её с разными аргументами
console.log(greet('Аня'));
console.log(greet('Макс'));
console
Макси

Видишь? Нажал ▶️ — код реально выполнился, внизу вывод. Это не картинка, это работающий JavaScript прямо в лекции. Можешь мысленно подставлять свои имена.

Параметры и аргументы

Параметр — это имя в скобках при объявлении (name). Аргумент — конкретное значение, которое передаёшь при вызове ('Аня'). Параметров может быть несколько:

params.js
function sum(a, b) {
  return a + b;
}
 
console.log(sum(2, 3));
console.log(sum(10, 25));
console.log(sum(100, -40));
console
02 · СТРЕЛОЧНЫЕ ФУНКЦИИ

Стрелочные функции

Та же идея, короче запись. Сейчас в React и современном коде пишут в основном так.

arrow.js
// классическая
function double1(n) {
  return n * 2;
}
 
// стрелочная — то же самое
const double2 = (n) => {
  return n * 2;
};
 
// если тело одно выражение — return не нужен
const double3 = (n) => n * 2;
 
console.log(double1(21));
console.log(double2(21));
console.log(double3(21));
console
Макси

Стрелка => читается как «превращается в». n => n * 2 — «эн превращается в эн умножить на два». Запомнишь так — путаться не будешь.

▸ Почему это важно для React

В React почти все обработчики событий и колбэки пишут стрелками: onClick={() => doSomething()}. Так что привыкай к синтаксису сейчас — дальше встретишь его сотни раз.

03 · ФУНКЦИИ И ДАННЫЕ

Функции работают с массивами

Самое полезное — прогонять функции по спискам данных. Вот где появляются map и filter.

Коротко напомню. filter отсеивает по условию, map преобразует каждый элемент. Обе принимают функцию. Запусти и посмотри разницу:

filter-map.js
const numbers = [1, 2, 3, 4, 5, 6, 7, 8];
 
// filter — оставить только чётные
const even = numbers.filter((n) => n % 2 === 0);
console.log('чётные:', even);
 
// map — удвоить каждое
const doubled = numbers.map((n) => n * 2);
console.log('удвоенные:', doubled);
 
// цепочка — сначала отсеять, потом преобразовать
const result = numbers
  .filter((n) => n % 2 === 0)
  .map((n) => n * 10);
console.log('цепочка:', result);
console
Рен

Обрати внимание: длина массива после filter может уменьшиться, а после map — никогда. map всегда возвращает столько же элементов, сколько было. Это инженерное правило, держи в голове.

Функции с объектами

На реальных проектах в массивах лежат объекты — это то, что приходит с сервера. Прогоним по ним функции:

objects.js
const products = [
  { name: 'Телефон', price: 15000, inStock: true },
  { name: 'Ноутбук', price: 80000, inStock: false },
  { name: 'Планшет', price: 25000, inStock: true },
];
 
// только то, что в наличии
const available = products.filter((p) => p.inStock);
console.log('в наличии:', available.map((p) => p.name));
 
// поднять цены на 10%
const newPrices = products.map((p) => p.name + ': ' + (p.price * 1.1));
console.log(newPrices);
console
«filter режет, map красит» «map всегда той же длины»
Раздел 02 · Типизация

Основы TypeScript

TypeScript — это JavaScript, который требует объяснений. Ты заранее говоришь, что хранит переменная, и редактор ловит ошибки до запуска. Разберём типы, интерфейсы и зачем это всё.

Рен

Дорогие студенты-Яндексоиды. Я инженер, поэтому скажу прямо: TypeScript экономит часы отладки. Чем раньше поймана ошибка, тем дешевле она стоит. TS ловит их прямо когда пишешь код.

01 · ЗАЧЕМ

Проблема, которую решает TS

В чистом JS переменная может внезапно сменить тип — и всё сломается там, где не ждёшь.

Запусти этот JS — он «работает», но выдаёт бред. Никто не подсказал, что складывать строку с числом — плохая идея:

problem.js
function add(a, b) {
  return a + b;
}
 
console.log(add(2, 3));      // 5 — ок
console.log(add('2', 3));    // '23' — упс, склеило строки
console.log(add('цена', 5)); // 'цена5' — полный бред
console
Рен

Вот ровно из-за этого в больших проектах появляется TypeScript. В TS такой вызов со строкой вместо числа подсветится красным ещё в редакторе — до того, как код вообще запустится.

▸ Как это работает технически

TypeScript не запускается в браузере напрямую. Ты пишешь .ts, компилятор проверяет типы и превращает код в обычный .js. То есть TS — это слой проверок поверх JavaScript на этапе написания.

02 · БАЗОВЫЕ ТИПЫ

Аннотации типов

Ты дописываешь после имени : тип — и теперь переменная держит только его.

JavaScript — тип не указан
TypeScript — тип явный
let name = 'Аня'; let age = 25; let active = true; // можно случайно сломать: name = 42; // молчит
let name: string = 'Аня'; let age: number = 25; let active: boolean = true; // поймает сразу: name = 42; // Ошибка! ✗

Основные типы, которые встретишь каждый день:

  • string — строки: 'привет', "текст"
  • number — любые числа: 42, 3.14, -7
  • boolean — true или false
  • string[] — массив строк
  • number[] — массив чисел
Макси

Запомни просто: двоеточие после имени — это «обещание». age: number значит «обещаю, тут всегда будет число». Нарушишь обещание — TS заметит.

Типы в функциях

Указываем типы параметров и тип того, что функция возвращает (после скобок):

typed-fn.ts
// (параметры с типами): тип результата
function add(a: number, b: number): number {
  return a + b;
}
 
add(2, 3);      // ок
add('2', 3);    // Ошибка! строка вместо числа
 
// стрелочная с типами
const greet = (name: string): string => {
  return 'Привет, ' + name;
};
▸ Почему примеры на этой странице не запускаются

TypeScript нельзя выполнить в браузере без компиляции, поэтому тут код показан для чтения. Но логика та же, что в JS с прошлой страницы — добавились только аннотации типов. Сами вычисления идентичны.

03 · ИНТЕРФЕЙСЫ

Интерфейсы — форма объекта

Интерфейс описывает, какие поля и какого типа должны быть у объекта. Это «договор».

interface.ts
// описываем форму объекта
interface User {
  id: number;
  name: string;
  email: string;
  age?: number;          // ? — поле необязательное
  readonly role: string; // readonly — менять нельзя
}
 
// теперь объект обязан соответствовать
const user: User = {
  id: 1,
  name: 'Иван',
  email: 'ivan@mail.ru',
  role: 'admin',
};
 
// массив таких объектов
const users: User[] = [user];
Рен

Интерфейс — это контракт. Один раз описал User — и везде, где он используется, редактор знает структуру. Опечатался в имени поля? Подсветит. Забыл обязательное поле? Подсветит. Это страховка от глупых ошибок.

Зачем это в команде

Когда над проектом работают десять человек, интерфейсы становятся общим языком. Один написал функцию, которая ждёт User — остальные сразу видят, что туда передавать. Не надо лезть в чужой код и разбираться.

Без типов: что внутри?
С интерфейсом: всё ясно
function save(user) { // что у user внутри? // name? имя? username? // надо лезть и искать... }
function save(user: User) { // редактор подскажет: // user.id, user.name, // user.email — всё видно }
«типы — это страховка, а не бюрократия» «опечатку поймают до запуска»
Раздел 03 · Интерфейсы

Основы React

React собирает интерфейсы из компонентов — как из кубиков Lego. Каждый компонент это функция, возвращающая кусок страницы. Жми ▶️ — увидишь, что отрисует код в браузере.

Кайл

Помнишь функции-станки с первой страницы? React — это станки, которые выдают не текст, а куски интерфейса. Сейчас покажу, и под каждым примером будет кнопка отрисовки результата.

▸ Как тут устроен запуск React

Настоящий React требует сборщика и не запускается в чистом браузере. Поэтому ▶️ под React-примерами показывает симуляцию результата — точно то, что отрисовал бы компонент. Код рядом — настоящий, рабочий React-синтаксис.

03 · MAP РИСУЕТ СПИСКИ

map() превращает данные в интерфейс

Вот связка всего. Массив данных → массив компонентов через тот самый .map().

Логика та же, что на первой странице. Только map теперь превращает не число в число, а объект — в карточку. Запусти — увидишь три карточки, отрисованные из массива:

ProductList.jsx
function ProductList() {
  const products = [
    { id: 1, name: 'Телефон', price: 15000 },
    { id: 2, name: 'Планшет', price: 25000 },
    { id: 3, name: 'Часы', price: 22000 },
  ];
 
  return (
    <div>
      {products.map((p) => (
        <ProductCard
          key={p.id}
          name={p.name}
          price={p.price}
        />
      ))}
    </div>
  );
}
результат в браузере
localhost:3000
Кайл

Смотри что вышло. Взяли массив products, через .map() каждый объект превратили в карточку, данные прокинули через props. Это связало всё: массивы, map, компоненты, props — в одной конструкции. Так и выглядит реальная разработка.

▸ Зачем key={p.id}

При отрисовке списка через map React требует уникальный key у каждого элемента — по нему он понимает, что изменилось, и не перерисовывает весь список. Бери id, а не индекс массива.

04 · СОСТОЯНИЕ

Состояние — память компонента

Props приходят сверху и не меняются. State — собственная память, которая живёт и меняется от действий пользователя.

Нажал лайк — счётчик вырос. За это отвечает useState. Ключевой момент: поменял состояние — React сам перерисовал. Запусти и пожми кнопку в результате:

Counter.jsx
import { useState } from 'react';
 
function Counter() {
  // [значение, функция-меняла] = useState(старт)
  const [count, setCount] = useState(0);
 
  return (
    <button onClick={() => setCount(count + 1)}>
      Лайков: {count}
    </button>
  );
}
результат в браузере
localhost:3000
Макси

Разбор const [count, setCount] = useState(0): count — текущее значение, setCount — функция чтобы менять, 0 — старт. Менять count напрямую нельзя, только через setCount — иначе React не заметит и не перерисует.

«поменял state — UI обновился сам» «это уже мини-приложение»

TypeScript в React + архитектура

Соединяем TS и React, а потом смотрим, как организовать растущее приложение, чтобы оно не превратилось в кашу. И знакомимся с FSD — поверхностно, для старта.

Дорогие студенты-Яндексоиды. Сейчас самое полезное для работы: типизированный React и то, как раскладывать файлы по полочкам. Без этого большой проект быстро становится болотом.

01 · TS + REACT

Типизируем компоненты

Props — это объект, а значит для него можно описать интерфейс. Тогда React-компонент станет типобезопасным.

ProductCard.tsx
// описываем форму props через интерфейс
interface ProductCardProps {
  name: string;
  price: number;
  inStock?: boolean;  // необязательное
}
 
// компонент принимает типизированные props
function ProductCard({ name, price }: ProductCardProps) {
  return (
    <div className="card">
      <h3>{name}</h3>
      <p>{price} ₽</p>
    </div>
  );
}
Макси

Заметь две вещи. Файл теперь .tsx, а не .jsx — буква t значит TypeScript. И {{ name, price }} — это «деструктуризация», достаём поля из props сразу, чтобы не писать props. каждый раз.

Состояние тоже типизируется

Counter.tsx
import { useState } from 'react';
 
function Counter() {
  // <number> — говорим, что состояние это число
  const [count, setCount] = useState<number>(0);
 
  return (
    <button onClick={() => setCount(count + 1)}>
      Лайков: {count}
    </button>
  );
}

Запустим типизированный пример — список пользователей, где у каждого свой тип роли:

UserList.tsx
interface User {
  id: number;
  name: string;
  role: 'admin' | 'user';  // только эти два значения!
}
 
function UserList() {
  const users: User[] = [
    { id: 1, name: 'Иван', role: 'admin' },
    { id: 2, name: 'Аня', role: 'user' },
  ];
 
  return (
    <div>
      {users.map((u) => (
        <div key={u.id}>{u.name} — {u.role}</div>
      ))}
    </div>
  );
}
результат в браузере
localhost:3000
▸ Что за role: 'admin' | 'user'

Это «union-тип» — поле может быть только одной из перечисленных строк. Напишешь role: 'moderator' — TS подсветит ошибку. Так типы защищают от опечаток в значениях, а не только в названиях полей.

02 · АРХИТЕКТУРА

Как не утонуть в файлах

Пока компонентов три — порядок не нужен. Когда их триста — без структуры наступает хаос.

Сначала все пишут просто: папка components, и туда сваливается всё подряд. Работает ровно до момента, когда ты не можешь найти нужный файл и не понимаешь, что от чего зависит.

Рен

Я это называю «папка-помойка». Сто файлов в одном месте, всё импортит всё, поменял одно — сломалось другое в неожиданном месте. Архитектура нужна именно чтобы этого не было.

Базовый принцип: группируй по смыслу

Первый шаг — раскладывать не по типу файла, а по смыслу. Не «все кнопки в одну кучу», а «всё про товары вместе, всё про пользователя вместе»:

✗ по типу файла
✓ по смыслу
components/ Button.tsx ProductCard.tsx UserAvatar.tsx CartItem.tsx hooks/ useUser.ts useCart.ts useProduct.ts
product/ ProductCard.tsx useProduct.ts user/ UserAvatar.tsx useUser.ts cart/ CartItem.tsx useCart.ts

В правом варианте всё про товар лежит рядом. Работаешь с товарами — открыл одну папку, всё под рукой. Это уже половина пути к нормальной архитектуре.

03 · FSD

Feature-Sliced Design

FSD — популярная методология раскладки кода для фронтенда. Сегодня только знакомимся: что это и зачем.

Кайл

FSD — это, по сути, набор правил «что куда класть и что от чего может зависеть». Звучит занудно, но именно это спасает большие проекты. Сейчас пройдёмся по верхам, в следующий раз разберём глубоко.

Слои FSD

Код делится на слои. Сверху — самое общее (всё приложение), снизу — самое переиспользуемое (мелкие кирпичики):

appвход в приложение: роутинг, провайдеры, глобальные стили
pagesстраницы целиком — то, что видит пользователь по адресу
widgetsкрупные самостоятельные блоки: шапка, лента, сайдбар
featuresдействия пользователя: «лайкнуть», «добавить в корзину»
entitiesбизнес-сущности: товар, пользователь, заказ
sharedпереиспользуемое без привязки к бизнесу: кнопки, утилиты, API
Рен

Логика слоёв простая: чем выше — тем «конкретнее и про этот проект», чем ниже — тем «универсальнее». Кнопка в shared не знает ничего про товары. А страница в pages знает про всё, что ниже.

Главное правило: импорты только вниз

Это сердце FSD. Слой может использовать только то, что лежит ниже него. Никогда наоборот.

направление зависимостей
pages
↓ можно
entities
↓ можно
shared
↑ наверх — НЕЛЬЗЯ

Почему так строго? Потому что это убирает запутанные связи. shared ничего не знает о том, кто его использует, поэтому его можно менять спокойно. А зависимости всегда текут в одну сторону — как и данные в React.

▸ Что разберём в следующий раз

Сегодня это обзор для общего понимания. В следующей лекции углубимся: сегменты внутри слоёв (ui / model / api), правила публичного API через index-файлы, и data-management — как данные ходят по приложению. Пока достаточно уловить идею слоёв и правило «импорт только вниз».

Раздел 01 · Бэкенд

Что такое бэкенд и первый сервер

Фронт ты уже трогал. Теперь вторая половина: код, который живёт на сервере, держит бизнес-логику и базу данных, и с которым фронт переписывается по HTTP. Поднимем сервер на Express и разберём, кто кому что отвечает.

Кайл

Дорогие студенты-Яндексоиды, переходим на тёмную сторону — на сервер. Тут нет кнопок и анимаций. Тут данные, правила и ответственность. Зато именно тут решается, что фронту вообще можно показывать.

01 · ЗАЧЕМ ОН НУЖЕН

Чему нельзя доверять браузеру

Бэкенд — это код, которому можно верить. Браузер у пользователя, его можно вскрыть и подправить. Сервер у тебя.

Поэтому на бэке живёт всё, что нельзя отдавать клиенту: проверка прав, цены и скидки, доступ к базе, пароли, платежи. Фронт красивый, но наивный: он просто рисует то, что прислал сервер. Решения принимает сервер.

  • Бизнес-логика — правила: можно ли забронировать этот слот, хватает ли денег.
  • База данных — единственный источник правды, фронт к ней напрямую не лезет.
  • Безопасность — аутентификация, права, валидация входных данных.
Золотое правило

Никогда не доверяй данным с фронта. Цену, роль юзера, id владельца — всё перепроверяй на сервере. Клиент может прислать что угодно, включая то, что ты не предусмотрел.

03 · ПЕРВЫЙ СЕРВЕР

Express за пять строк

Node.js позволяет запускать JavaScript вне браузера. Express — лёгкий фреймворк поверх него, который превращает «слушать порт и разбирать HTTP» в пару понятных строк.

server.js
const express = require('express');
const app = express();

app.use(express.json());          // понимать JSON в теле запросов

// маршрут: на GET /health отвечаем, что живы
app.get('/health', (req, res) => {
  res.status(200).json({ status: 'ok' });
});

app.listen(3000, () => {
  console.log('Сервер слушает http://localhost:3000');
});
Макси

Вся суть тут: app слушает порт, на каждый запрос подбирает обработчик по методу и пути, и тот зовёт res.json(). Ниже — та же логика обработчика чистым JS, её можно запустить прямо здесь.

handler.js
// в памяти сервера лежат брони (потом это будет БД)
const bookings = [
  { id: 1, court: 3, time: '09:00' },
  { id: 2, court: 1, time: '12:00' },
];

// обработчик GET /bookings — чистая функция: на входе запрос, на выходе ответ
function getBookings() {
  return { status: 200, body: bookings };
}

const response = getBookings();
console.log('status:', response.status);
console.log('body:', response.body);
console
Бэкенд — это место, где «у меня на машине работает» наконец-то правда, потому что машина одна и она твоя.

Раздел 02 · Роутинг

Маршруты и обработка запросов

Сервер должен понимать, какой запрос куда вести. Это роутинг: метод + путь → обработчик. Разберём req/res, параметры, middleware, и поднимем живой мок-API, который реально отвечает на кнопки.

Кайл

Роутинг — это диспетчерская. Пришёл запрос, смотрим: какой метод, какой путь, и отправляем нужному обработчику. Не нашли подходящий — отвечаем 404. Всё.

01 · МАРШРУТ

Метод + путь → обработчик

Один маршрут = глагол (метод) + адрес (путь) + функция, которая на это отвечает.

Двоеточие в пути — это параметр. /bookings/:id ловит и /bookings/1, и /bookings/42, а само значение кладёт в req.params.id.

routes.js
app.get('/bookings',     getAllBookings);    // список
app.get('/bookings/:id', getBookingById);   // одна бронь по id
app.post('/bookings',    createBooking);     // создать
app.delete('/bookings/:id', deleteBooking);  // удалить

// внутри обработчика достаём данные запроса:
function getBookingById(req, res) {
  const id = req.params.id;        // из пути /bookings/:id
  const sort = req.query.sort;     // из ?sort=time
  // ... найти и вернуть
  res.status(200).json(booking);
}
req и res

req — это входящий запрос: params (из пути), query (из ?строки), body (тело POST), headers. res — твой ответ: res.status(код).json(данные). Вся обработка крутится вокруг этих двух объектов.

02 · MIDDLEWARE

Конвейер перед обработчиком

Middleware — это функции, через которые запрос проходит по дороге к обработчику. Каждая может что-то проверить, дополнить или зарубить. Вызвал next() — поехали дальше, не вызвал — запрос застрял (например, отказ по правам).

middleware.js
// логируем каждый запрос
app.use((req, res, next) => {
  console.log(`${req.method} ${req.url}`);
  next();                          // пропускаем дальше по конвейеру
});

// пускаем дальше только с валидным токеном
function auth(req, res, next) {
  if (!req.headers.authorization) {
    return res.status(401).json({ error: 'нужен токен' });
  }
  next();
}

app.get('/bookings', auth, getAllBookings);  // auth сработает ДО обработчика
Рен

Порядок middleware = порядок конвейера. express.json() парсит тело, логгер пишет, auth проверяет права, и только потом обработчик. Ошибку ловит специальный error-middleware в самом конце. Это тот же принцип, что цепочка .filter().map() — данные текут через звенья.

Раздел 03 · SOLID

SOLID: пять правил, чтобы код не сгнил

Сервер живёт годами и его правят десятки людей. SOLID — пять принципов, которые держат код гибким и не дают ему превратиться в один гигантский класс, который страшно трогать. Разберём каждый на бэкенд-примере.

SOLID звучит как заклинание, но за каждой буквой простая мысль. Тыкай буквы — расскажу по одной. Главная из них для нас — последняя, D, на ней держится слоистая архитектура.

02 · НА ПРАКТИКЕ

Божественный объект против разделения

Самое частое нарушение у новичков — God Object: один класс делает всё. Принимает запрос, считает логику, лезет в базу. Поменялась БД — лезешь в тот же файл, где бизнес-логика. Поменялось правило — туда же. Всё спутано.

разделено (S + D) ✓
God Object ✗
// контроллер — только HTTP // сервис — только логика // репозиторий — только БД каждый меняется по своей причине
class BookingController { handle(req, res) { // парсит запрос // считает цену // пишет SQL // шлёт письмо } // всё в куче }
Рен

Принцип D (инверсия зависимостей) — самый важный на практике. Сервис не должен знать, что там за база. Он зависит от интерфейса репозитория. Запусти пример: подменяем реальный репозиторий на мок, а сервис даже не замечает.

dip.js
// сервис зависит от АБСТРАКЦИИ репозитория, а не от конкретной БД
function createBookingService(repo) {
  return {
    book(court, time) {
      if (repo.isTaken(court, time)) {
        return { ok: false, reason: 'слот занят' };
      }
      const saved = repo.save({ court, time });
      return { ok: true, booking: saved };
    },
  };
}

// в тестах подсовываем мок-репозиторий (никакой настоящей БД)
const fakeRepo = {
  taken: [{ court: 3, time: '09:00' }],
  isTaken(c, t) { return this.taken.some(x => x.court === c && x.time === t); },
  save(b) { return { id: 42, ...b }; },
};

const service = createBookingService(fakeRepo);
console.log(service.book(3, '09:00'));   // занят
console.log(service.book(1, '12:00'));   // ok, id 42
console

Раздел 04 · Архитектура

Слоистая архитектура

SOLID на уровне всего приложения превращается в слои. Запрос проходит сверху вниз через чёткие уровни, каждый знает только соседа. Это бэкенд-родственник FSD из прошлых лекций: те же границы, та же дисциплина.

Кайл

Три главных слоя: контроллер ловит HTTP, сервис думает бизнес-логику, репозиторий говорит с базой. Чужую работу никто не делает. Поменял базу — трогаешь только репозиторий. Поменял правило — только сервис.

01 · СЛОИ

Кто за что отвечает

  • Controller / Router — граница с HTTP. Достал params/body, позвал сервис, отдал res.json(). Бизнес-логики тут нет.
  • Service — чистая бизнес-логика. Правила, проверки, расчёты. Не знает про HTTP и не знает про SQL.
  • Repository — доступ к данным. Прячет за собой SQL/ORM. Сервис просит «дай брони на корт 3», репозиторий разбирается как.
  • Database — Postgres, источник правды.
src/ ├─ routes/ bookings.routes.js # пути → контроллеры ├─ controllers/ bookings.controller.js # HTTP-граница ├─ services/ bookings.service.js # бизнес-логика ├─ repositories/ bookings.repo.js # доступ к БД └─ db/ pool.js # подключение к Postgres
Связь с FSD

Тот же принцип, что правило импортов в FSD: зависимости текут в одну сторону. Контроллер знает сервис, сервис знает репозиторий, репозиторий знает базу. Назад — никогда. База ничего не знает о контроллере.

03 · В КОДЕ

Один эндпоинт, три слоя

Тот же GET /bookings/:id, разрезанный по слоям. Видно, как каждый зовёт только следующего и не лезет в чужое.

layers.js
// --- controller: только HTTP ---
async function getBookingById(req, res) {
  const booking = await bookingService.getById(req.params.id);
  if (!booking) return res.status(404).json({ error: 'не найдено' });
  res.status(200).json(booking);
}

// --- service: только логика, не знает про SQL ---
const bookingService = {
  async getById(id) {
    const b = await bookingRepo.findById(id);
    return b && b.isPublic ? b : null;     // бизнес-правило
  },
};

// --- repository: только данные, прячет SQL ---
const bookingRepo = {
  async findById(id) {
    const { rows } = await pool.query(
      'SELECT * FROM bookings WHERE id = $1', [id]
    );
    return rows[0];
  },
};
Контроллер, который сам пишет SQL — это сантехник, который заодно проектирует дом
Рен

Заметь $1 в SQL вместо склейки строк. Это параметризованный запрос — защита от SQL-инъекций. Никогда не вставляй данные пользователя прямо в текст запроса, только через параметры. Это правило не обсуждается.

Раздел 05 · База данных

Postgres, SQL и базовые библиотеки

Под всем этим лежит база. Postgres — реляционная: данные в таблицах, связанных ключами. Разберём таблицы, базовый SQL с живой песочницей, как Node с базой говорит, и набор библиотек, без которых не обходится ни один проект.

Кайл

Реляционная база — это таблицы, как листы в Excel, только строгие и связанные. У каждой строки есть id (первичный ключ). Ссылка из одной таблицы на другую — внешний ключ. Вот и вся базовая идея.

01 · ТАБЛИЦЫ

Строки, столбцы, ключи

Две таблицы из нашего букинга. У users свой id. В bookings поле user_id ссылается на users.id — это связь «чья бронь».

Зачем ключи

Первичный ключ (PK) — уникальный паспорт строки. Внешний ключ (FK) — связь между таблицами. По ним делают JOIN: «дай брони вместе с именами их владельцев». База сама следит, чтобы ссылки не висели в пустоту.

02 · SQL

Язык запросов к базе

SQL — это как ты разговариваешь с базой. Четыре главных глагола: читать, создавать, менять, удалять.

03 · NODE ↔ POSTGRES

Как код говорит с базой

Два пути. Драйвер pg — ты пишешь SQL руками (максимум контроля). ORM вроде Prisma/TypeORM — пишешь на объектах, SQL генерится сам (быстрее, но магия).

pg (сырой SQL)
Prisma (ORM)
const { rows } = await pool.query( 'SELECT * FROM users WHERE id=$1', [id] ); const user = rows[0];
const user = await prisma.user .findUnique({ where: { id } }); // SQL сгенерится сам
Параметры, не склейка

И там, и там данные идут параметрами ($1 или { id }), а не вклеиваются в строку запроса. Склеишь руками — получишь SQL-инъекцию, классическую дыру, через которую сливают базы.

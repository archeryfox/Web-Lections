Раздел 01 · Сеть

Как фронт и бэк разговаривают

Прежде чем таскать данные по проекту, надо понять откуда они вообще берутся. Сейчас разберём, что происходит между браузером и сервером, что такое HTTP, коды ответов и JSON. Всё наглядно и кликабельно.

Кайл

Дорогие студенты-Яндексоиды, начнём с фундамента. Фронтенд живёт в браузере, данные живут на сервере. Между ними — сеть. Всё, что мы делаем дальше, это переписка двух программ через интернет.

01 · КЛИЕНТ И СЕРВЕР

Двое на проводе

Браузер (клиент) спрашивает. Сервер (бэкенд) отвечает. Точка.

Когда ты открываешь страницу, браузер по имени сайта находит его IP через DNS (телефонная книга интернета), стучится на сервер и говорит: «дай мне вот это». Сервер думает, лезет в базу, и присылает ответ. Один запрос — один ответ. Сервер сам тебе ничего не шлёт, пока не спросишь (если это не вебсокеты, но это другая история).

Красный пакет — запрос, зелёный — ответ. В реальности туда-обратно это десятки миллисекунд, но цикл всегда один: спросил → подождал → получил. Запомни ритм, на нём держится весь async.

02 · HTTP-МЕТОДЫ

Глаголы запроса

HTTP — это протокол, язык переписки. У каждого запроса есть метод — что мы хотим сделать с ресурсом. Их немного, и они читаются как глаголы.

Метод
Что делает
GET
Прочитать. «Дай мне список юзеров.» Ничего не меняет.
POST
Создать. «Заведи нового юзера вот с этими данными.»
PUT / PATCH
Обновить. PUT меняет целиком, PATCH — кусочек.
DELETE
Удалить. «Снеси заказ №42.»
Правило

GET только читает и не имеет тела. Если ты что-то меняешь на сервере — это никогда не GET. Иначе поисковый робот, зайдя по ссылке, случайно удалит тебе пол-базы.

03 · КОДЫ ОТВЕТОВ

Сервер отвечает цифрой

На каждый запрос сервер возвращает трёхзначный код статуса. Первая цифра — категория. Это первое, на что смотришь, когда что-то сломалось. Потыкай:

  • 2xx — всё хорошо, держи данные.
  • 3xx — иди в другое место (редирект, кэш).
  • 4xx — ошибся ты (клиент). Кривой запрос, нет прав, не туда.
  • 5xx — упал сервер. Не твоя вина, иди к бэкендерам.
4xx — это «ты дурак», 5xx — это «я дурак»
04 · JSON

Формат, на котором все договорились

Данные по сети летят текстом. Нужен формат, который понимают и JS, и Python, и Go, и кто угодно. Этот формат — JSON (JavaScript Object Notation). Объекты в фигурных скобках, массивы в квадратных, строки в кавычках. Выглядит как объект JS, но это просто текст.

Макси

Ключевая мысль: по сети летит строка. JSON.parse превращает строку в живой объект, JSON.stringify — наоборот. Жми ▶️, увидишь оба превращения.

json.js
// то, что реально прилетело с сервера — это ТЕКСТ
const raw = '{"name":"Аня","age":27,"skills":["js","ts"]}';
console.log(typeof raw);            // string — пока просто строка

// парсим текст в настоящий объект
const user = JSON.parse(raw);
console.log(typeof user);           // object
console.log(user.name, user.age);   // Аня 27
console.log(user.skills[0]);        // js

// и обратно — объект в строку, чтобы отправить на сервер
const back = JSON.stringify({ ok: true, count: 3 });
console.log(back);                  // {"ok":true,"count":3}
console
Зачем это знать фронтендеру

Сервер почти всегда отдаёт JSON. Любой fetch заканчивается на .json(). Любая ошибка «cannot read property of undefined» часто значит, что структура JSON не та, что ты ждал. Поэтому дальше — валидация.

Раздел 02 · Инструменты

Чем делаем запросы: fetch и axios

Теперь сами стучимся на сервер из кода. Два инструмента: нативный fetch и библиотека axios. Демки ниже бьют по настоящему публичному API — это реальные запросы, а не картинки.

Кайл

fetch встроен в браузер, ставить ничего не надо. axios — отдельная библиотека, которая делает то же самое, но удобнее. Сначала fetch, потом разберём чем axios лучше.

01 · FETCH

Нативный способ

fetch возвращает промис — обещание, что ответ придёт позже. Поэтому его ждут через await.

Тонкость номер один: fetch отдаёт ответ в два этапа. Сначала прилетают заголовки и статус (первый await), потом распаковываешь тело через .json() (второй await). Тонкость номер два: fetch не считает ошибкой коды 404 или 500 — для него «сервер ответил» уже успех. Проверять response.ok приходится руками.

fetch.js
// реальный запрос на публичный тестовый API
const res = await fetch('https://jsonplaceholder.typicode.com/users/2');

console.log('статус:', res.status);   // 200
console.log('всё ок?', res.ok);       // true

// второй await — распаковываем тело из JSON
const user = await res.json();
console.log('имя:', user.name);
console.log('город:', user.address.city);
console
нажми кнопку — увидишь живой ответ настоящего сервера здесь
Грабли fetch

fetch НЕ кидает ошибку на 404/500. Этот код спокойно «отработает» на сломанном запросе и упадёт уже на user.name. Всегда проверяй if (!res.ok) throw ... сам.

02 · AXIOS

То же, но с комфортом

axios — обёртка над тем же HTTP, но снимает рутину. Что он даёт сверху:

  • Сам парсит JSON — никакого второго .json(), данные сразу в res.data.
  • Сам кидает ошибку на 4xx/5xx — попадаешь в catch, а не ловишь баг на ровном месте.
  • baseURL и interceptors — один раз настроил адрес и токен, дальше пишешь короткие пути. Перехватчики цепляют заголовки и логируют каждый запрос централизованно.
axios.js
import axios from 'axios';

// настроил один раз на весь проект
const api = axios.create({
  baseURL: 'https://api.yandex.ru',
  timeout: 5000,
});

// interceptor: вешаем токен на каждый запрос автоматически
api.interceptors.request.use((config) => {
  config.headers.Authorization = `Bearer ${getToken()}`;
  return config;
});

// сам запрос — коротко, JSON уже распарсен, ошибки в catch
const { data } = await api.get('/users/2');
console.log(data.name);
демо «как будто axios» (тот же реальный API, axios сам бы распарсил JSON):
Рен

На пет-проекте хватит fetch. Как только появляется авторизация, базовый адрес и единая обработка ошибок на десятках запросов — axios экономит кучу копипасты. Это вопрос масштаба, а не вкуса.

03 · ASYNC / AWAIT

Как читать асинхронный код

Запрос идёт время. JS не стоит и не ждёт — он идёт дальше, а результат приходит потом. async/await позволяет писать асинхронный код так, будто он синхронный: сверху вниз, по-человечески.

async.js
function getData() {
  // имитируем задержку сети на 600мс
  return new Promise(resolve => {
    setTimeout(() => resolve({ name: 'Аня', online: true }), 600);
  });
}

console.log('1. отправляю запрос...');
const user = await getData();        // тут код "ждёт" не блокируя
console.log('2. пришёл ответ:', user.name);
console.log('3. поехали дальше');
console
Мнемоника

async на функции = «внутри будут ожидания». await перед вызовом = «постой тут, пока не придёт результат». Всё, что после await, выполнится только когда данные на руках.

Раздел 03 · Типы

Объекты, классы и Zod

Данные приехали. Теперь надо их описать типами и не доверять серверу на слово. Разберём объекты vs классы, почему TS-типы исчезают в рантайме, и как Zod проверяет данные по-настоящему.

Кайл

Данные в JS живут в объектах. TypeScript добавляет к ним типы — описание формы. Но есть подвох на границе с сервером, и его закрывает Zod. Разберём по порядку.

01 · ОБЪЕКТЫ

Базовая структура данных

Объект — это набор пар «ключ: значение». 90% данных во фронте — объекты и массивы объектов.

object.js
// объект — данные сгруппированы по смыслу
const user = {
  name: 'Аня',
  age: 27,
  isAdmin: false,
};

console.log(user.name);          // доступ по ключу
user.age = 28;                   // меняем поле

// массив объектов — то, что обычно приходит с сервера
const users = [
  { name: 'Аня', age: 27 },
  { name: 'Макс', age: 31 },
];
console.log(users.map(u => u.name));   // ['Аня', 'Макс']
console
02 · КЛАССЫ vs ИНТЕРФЕЙСЫ

Когда что

Тут новички путаются. Разница простая по сути.

  • interface / type — это только описание формы. Существует на этапе компиляции, в рантайме его нет. Не создаёт ничего, просто говорит «объект должен выглядеть так».
  • class — это фабрика объектов с поведением. Существует в рантайме, через new создаёт экземпляры, держит данные и методы вместе.
interface — форма данных
class — объект с логикой
interface User { name: string; age: number; } // просто контракт, кода нет
class User { constructor(public name: string) {} greet() { return `Привет, ${this.name}`; } } // new User('Аня').greet()
Практика фронта

В React-проектах ты в 95% случаев берёшь interface/type для описания данных (props, ответы API, состояние). Классы всплывают редко — для сервисов или сложной доменной логики. Не плоди классы там, где хватает интерфейса.

03 · ГЛАВНЫЙ ПОДВОХ

Типы врут на границе сети

Вот ловушка, на которую попадаются все. Ты пишешь тип ответа сервера. TS верит тебе на слово и больше ничего не проверяет — типы исчезают при компиляции. А сервер возьмёт и пришлёт не то. И ты узнаешь об этом, когда приложение уже упало у пользователя.

lie.js
// ты ДУМАЕШЬ что age — число (так написано в типе)
// но сервер прислал строку. TS уже ничего не проверяет в рантайме.
const fromServer = { name: 'Аня', age: '27' };   // ← строка!

// считаем средний возраст — и получаем мусор
const avg = (fromServer.age + 3);
console.log('ожидали 30, получили:', avg);   // "273" — склейка строк!
console.log('тип:', typeof avg);             // string

// баг тихо протёк дальше по приложению
console
Макси

Видишь? TS на этапе написания зелёный, всё «типизировано». А в рантайме сервер подсунул строку, и 27 + 3 стало "273". Типы не защищают от реальных данных. Нужен сторож на входе.

04 · ZOD

Валидация, которая работает в рантайме

Zod — это схема данных, которая проверяет по-настоящему, во время выполнения. Ты описываешь форму один раз, и Zod на входе режет всё, что не подходит. Бонус: из схемы автоматически выводится TS-тип через z.infer — один источник правды.

schema.ts
import { z } from 'zod';

// одна схема = и проверка в рантайме, и тип для TS
const UserSchema = z.object({
  name: z.string().min(1),
  age: z.number().min(0).max(120),
  email: z.string().email(),
});

// тип выводится из схемы автоматически
type User = z.infer<typeof UserSchema>;

// на границе сети: проверяем ответ ДО того как доверять
const res = await fetch('/api/user/2');
const data = await res.json();
const parsed = UserSchema.safeParse(data);

if (parsed.success) {
  use(parsed.data);   // тут уже гарантированно правильная форма
} else {
  console.error(parsed.error);   // сервер прислал мусор — ловим тут
}
Рен

Ниже — живая песочница. Логика та же, что у Zod: схема ждёт непустое имя, возраст-число 0..120 и валидный email. Подсунь сломанные данные и посмотри, как валидатор их завернёт.

схема: { name: string(min 1), age: number(0..120), email: email }
результат проверки появится здесь
Где это живёт в проекте

Zod-схемы кладут в слой данных — рядом с запросами, в api/model сущности. Граница «сеть → приложение» это единственное место, где данные надо валидировать. Прошли схему — дальше им можно верить везде.

Раздел 04 · Состояние

Дата-менеджмент: Zustand vs Redux

Данные получены и проверены. Где они теперь живут, пока приложение работает? Разберём теорию состояния, проблему prop drilling, и два инструмента: минималистичный Zustand и классический Redux. Со живым стором, который можно потыкать.

Кайл

Состояние — это память приложения прямо сейчас: что в корзине, кто залогинен, какой фильтр выбран. Вопрос дата-менеджмента простой: где это хранить, чтобы любой компонент мог взять и не утонуть.

01 · ТЕОРИЯ

Два вида состояния

Сначала важное различие, которое экономит кучу нервов:

  • Server state — данные, которые живут на сервере, а у тебя их копия: список товаров, профиль. Их надо грузить, кэшировать, обновлять (этим часто рулит отдельный инструмент типа TanStack Query).
  • Client state — то, что существует только в браузере: открыто ли меню, что в корзине, тема. Вот этим и занимаются Zustand / Redux.
Проблема prop drilling

Без стора состояние приходится протаскивать пропсами через 5 уровней компонентов: A → B → C → D → E, хотя нужно только A и E. Промежуточные компоненты тащат чужие пропсы просто как курьеры. Стор убирает этот туннель: положил в одно место, взял где угодно.

02 · ZUSTAND

Стор как один объект

Zustand до неприличия простой. Один create, внутри состояние и функции, которые его меняют. Никаких провайдеров, редьюсеров и церемоний.

cartStore.ts
import { create } from 'zustand';

// весь стор — один хук
export const useCart = create((set) => ({
  items: [],
  total: 0,
  // экшены прямо тут, рядом с данными
  add: (product) => set((state) => ({
    items: [...state.items, product],
    total: state.total + product.price,
  })),
  clear: () => set({ items: [], total: 0 }),
}));

// в компоненте — берёшь ровно то, что нужно (селектор)
function Badge() {
  const count = useCart((s) => s.items.length);
  return <span> {count}</span>;
}
Макси

Ниже — настоящий работающий стор (та же механика: состояние + set + подписчики). Жми «В корзину» и смотри: меняется одно место, а оба подписчика — счётчик и сумма — перерисовываются сами. Никто никому не передавал пропсы.

03 · REDUX

Классика с церемонией

Redux старше и строже. Данные неизменяемы, любое изменение идёт через action → reducer → новый стейт. Поток строго однонаправленный и предсказуемый, но кода ощутимо больше.

cartSlice.ts
import { createSlice } from '@reduxjs/toolkit';

const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [], total: 0 },
  reducers: {
    // редьюсер: получает стейт и action, возвращает новый стейт
    add: (state, action) => {
      state.items.push(action.payload);
      state.total += action.payload.price;
    },
    clear: (state) => { state.items = []; state.total = 0; },
  },
});

export const { add, clear } = cartSlice.actions;
// + нужен store, Provider в корне, useSelector/useDispatch в компонентах
Zustand
Redux Toolkit
• один create, и всё • нет Provider-обёртки • экшены рядом с данными • мало кода • меняешь стейт напрямую через set
• slices + store + Provider • action → reducer → стейт • строгий однонаправленный поток • больше boilerplate • мощный DevTools, time-travel
Рен

Выбор по масштабу. Маленькое-среднее, команда хочет скорость — Zustand. Огромное приложение, сложные взаимозависимости, нужен жёсткий аудит каждого изменения и time-travel отладка — тогда дисциплина Redux окупается. Для большинства фронтов сегодня Zustand закрывает потребность.

Redux: 40 строк чтобы поменять одно число. Zustand: set(n => n+1)
Раздел 05 · Архитектура

FSD: торт, который не разваливается

Финал. У нас есть запросы, типы, валидация и сторы. Теперь надо разложить это по проекту так, чтобы через год в нём можно было жить. Это и есть Feature-Sliced Design — разрезаем приложение на слои, как торт на коржи.

Кайл

Дорогие студенты-Яндексоиды, код без архитектуры — это спагетти: дёрнул одну нитку, размотался весь клубок. Архитектура — это правила, где что лежит и кто кого может звать. FSD — самый популярный такой свод правил во фронте.

01 · ЗАЧЕМ

Почему правильная архитектура — это красиво

Можно ведь свалить всё в папки components, utils, api и группировать по типу файла. Работает... пока проект маленький. Потом фича размазана по десяти папкам, и чтобы понять одну кнопку, открываешь полпроекта.

FSD группирует по смыслу: всё про авторизацию — в одном месте, всё про корзину — в другом. Удалить фичу = удалить папку. Найти баг = знаешь где искать. Новый человек в команде ориентируется за день.

по смыслу (FSD) ✓
по типу (каша) ✗
features/ auth/ cart/ entities/ user/ product/
components/ LoginForm.tsx CartButton.tsx UserCard.tsx utils/ authApi.ts cartApi.ts
Главный профит

Когда архитектура задаёт чёткие границы, ты держишь в голове один маленький кусок, а не весь проект. Меняешь одно — не ломается другое. Это не эстетика ради эстетики, это скорость и спокойный сон.

02 · ТОРТИК

Слои — это коржи

FSD режет приложение на горизонтальные слои. Сверху — конкретное и зависимое, снизу — общее и независимое. Наведи на корж:

appточка входа, роутер, провайдеры
pagesстраницы, собранные из виджетов
widgetsсамостоятельные блоки страницы
featuresдействия пользователя
entitiesбизнес-сущности
sharedфундамент: ui-кит, api, утилиты
Нажми на слой
Каждый корж — это уровень ответственности. Чем выше, тем ближе к конкретному экрану.
Рен

Запомни направление: верхние коржи зависят от нижних, никогда наоборот. shared не знает про features, а app знает про всех. Самый общий код — внизу, самый конкретный — сверху.

03 · СЛАЙСЫ И СЕГМЕНТЫ

Режем корж дальше

Внутри слоя (кроме app и shared) код делится на слайсы — это бизнес-домены. В entities слайсы это user, product, order. В features — auth, add-to-cart. Слайс = вертикальный кусок одной темы.

А внутри каждого слайса — сегменты, всегда одни и те же по смыслу:

  • ui — компоненты, как это выглядит.
  • model — состояние и логика: тут живут zustand-сторы, типы, zod-схемы.
  • api — запросы на сервер: тут живут fetch/axios.
  • lib — вспомогательные функции этого слайса.
src/ ├─ entities/ # бизнес-сущности │ └─ product/ # ← слайс │ ├─ ui/ # ProductCard.tsx │ ├─ model/ # store.ts, types.ts, schema.ts (zod) │ └─ api/ # getProducts.ts (fetch/axios) ├─ features/ # действия: add-to-cart, auth ├─ widgets/ # Header, ProductList ├─ pages/ # CatalogPage собирает виджеты └─ shared/ # ui-кит, базовый api-клиент, утилиты
Правило импортов

Слой может импортировать только из слоёв НИЖЕ себя. features берёт из entities и shared, но никогда из widgets. Это правило в одну строку и есть весь секрет: зависимости текут строго вниз, циклов не возникает, клубок не запутывается.

04 · ВСЁ ВМЕСТЕ

Путь данных через слои

А вот ради чего всё затевалось. Смотри, как материал всех пяти разделов встаёт по местам, когда пользователь жмёт кнопку. Запусти поток:

Вот и вся картина, Яндексоиды. Сеть приносит данные → fetch их забирает → Zod проверяет → Zustand хранит → React рисует. А FSD говорит, в какой папке каждый из этих шагов живёт. Архитектура — это не бюрократия, это карта, по которой не заблудишься.
